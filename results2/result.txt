The tests show that on the server, the new versions are significantly faster than the onld ones. Also the best variants seem to be (all/(#threads*16), 1/4) and (all/(#threads*8), 1/16). There will be a third round of testing of these two with the full scale testing.

  Interesting notes: on my PC and laptop, the versions with up to 8 threads are slower than the old version. For 8 threads this can be understandable, since we do introduce more communication and there wasn't that much load inbalance in the first place. However, on the server the new version is faster, in contrast to my PC. On my laptop, the runtime for 8 threads went from 157s to 177s, so also increased. More curiously: also for 1 thread the runtime went up. On my PC by about 5% again, on my laptop from 15.06min to 15.37min. This isn't so easily explained: I introduced a condition into the new version that makes sure that for only one worker, the behaviour is exactly as before. Nothing changed, the same work is done and there is no communication. The time should be exactly the same. Why does this happen?

  First of all, it should be conceptually clear that basically all runtime must lie in the snowflake loop per pixel. Checking with perf shows that this is indeed 99.98% of the runtime for 1 thread. The loop is often mispredicted and is very data-bound: the first load instruction of the snowflake from the array is slow and the next arithmetic instructions depend on it and so on. This is the same for both the old and new version. Again, the actual code for this loop is the exact same for the static and dynamic version. But, looking at the disassembly, we notice that it isn't perfectly the same. In fact, some instructions are mixed up. This easily results in 5% performance difference, since there is no instruction-level parallelism and we are very databound. So the reason for this apparent regression is just random change: the compiler is very subsceptible to the context of the code which results in slightly different assembly. Since those instructions are the bottleneck, it results in noticably different runtimes. It is unclear why the compiler on my PC and laptop generate worse code for the new version / what change in the context makes this happen. The compiler on the server behaves a bit differently and it doesn't have the same flaw. So ultimately: there is no actual regression and we did nothing wrong, we just got f*cked by the performance lottery.
